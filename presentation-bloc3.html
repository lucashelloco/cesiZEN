02 Déployer

Vue d'ensemble

Le trajet d'une modification, du poste local à la production

VI.A

Trois environnements, articulés sur les branches Git. Chaque changement « monte » d'un environnement au suivant — aucun code non validé n'atteint la production.

Développement
poste local · npm run dev branche feature/*
  • Objectif — intégrer le travail en cours
  • Déclencheur — fusion d'une feature/*
  • Base — PostgreSQL local (Docker)
  • Données — jeu de seed
  • Accès — développeur
→
Test / Recette
Pull Request CI GitHub Actions Preview Vercel (URL/PR)
  • Objectif — recetter avant la fusion
  • Déclencheur — ouverture ou mise à jour d'une PR
  • Base — branche Neon de test
  • Données — test anonymisées
  • Accès — relecteur, par lien
→
Production
branche main (protégée) Vercel Production tag vX.Y.Z
  • Objectif — servir les utilisateurs réels
  • Déclencheur — fusion sur main, puis tag
  • Base — Neon production
  • Données — réelles
  • Accès — public
Le principe Une seule porte d'entrée vers la production : la Pull Request. Elle déclenche la CI, génère un environnement de recette jetable, et ne peut être fusionnée que si tout est vert.

Voilà la chaîne complète. Insister sur la continuité : le même schéma vaut pour une correction d'une ligne comme pour une fonctionnalité entière. Le point clé pour le jury : la Pull Request est le point de contrôle unique — c'est là que la CI valide et que l'environnement de recette apparaît automatiquement. Les trois environnements ne sont pas trois serveurs à administrer : ce sont trois états d'une même chaîne.

03 Déployer

Choix d'hébergement

Pourquoi le serverless, et pas un serveur à moi

VI.A

Le besoin dimensionnant

  • Application grand public : fréquentation variable et imprévisible
  • Des pics liés à la communication, un usage diurne, des nuits creuses
  • Une seule personne pour développer et exploiter

Le dimensionnement ne pouvait donc pas être fixe : il devait suivre la charge, sans personne pour l'ajuster.

Élasticité

La capacité monte et descend seule. Pas de surcoût en période creuse, pas de saturation aux pics.

Coût à l'usage

Facturation à la consommation ; les paliers gratuits suffisent en phase de lancement.

Exploitation réduite

Aucun OS ni serveur à patcher : moins de maintenance, et une surface d'attaque plus faible.

Proximité réseau

Le CDN Vercel sert les ressources statiques au plus près de l'utilisateur.

Neon — le même raisonnement pour la base

PostgreSQL managé, scale-to-zero, connection pooler indispensable au serverless, et des branches de base de données pour les environnements de test. Compatible nativement avec Prisma.

Écartés — et pourquoi

VPS + Docker, AWS, Kubernetes : plus de contrôle, mais une complexité et un coût d'exploitation disproportionnés pour ce projet. Docker reste utilisé — pour la base en local.

Le réflexe du jury sera : « pourquoi pas Docker sur un VPS ? ». Ma réponse tient en une phrase : je dimensionne pour une charge que je ne peux pas prévoir, avec une équipe d'une personne. Le serverless me donne l'élasticité et me retire l'administration système. Et Vercel est l'éditeur de Next.js : l'intégration est native. Précision honnête : ce n'est pas un choix universel — sur une charge stable et prévisible, un VPS coûterait moins cher.

La branche main est protégée

  • Toute modification passe par une Pull Request
  • La CI doit être verte avant la fusion
  • Les pushs directs sont refusés — vérifié

Versionnement sémantique

vMAJEUR.MINEUR.CORRECTIF

  • MAJEUR — changement incompatible
  • MINEUR — ajout rétrocompatible
  • CORRECTIF — correction seule

Bonnes pratiques appliquées

  • Gabarit de PR avec check-list : lint, tests, CI verte, aucun secret, ticket lié
  • Commits conventionnels (feat, fix, docs)
  • Documentation versionnée avec le code
Pour le client Une version en production est identifiable (un tag), traçable (l'historique des PR) et réversible (on sait exactement où revenir).

Le cahier des charges demande explicitement la méthodologie de suivi des versions et l'outil. L'outil, c'est Git + GitHub. La méthodologie, c'est ce trajet : isoler, intégrer, contrôler, livrer, figer. Le message à faire passer : le tag SemVer n'est pas de la décoration — c'est ce qui permet de dire au Ministère « la production tourne en v1.0.0 » et de revenir en arrière sans hésiter.

Choix d'outil · versioning

GitHub, GitLab ou Bitbucket ?

Critère GitHub — retenu GitLab Bitbucket
Hébergement Git + revue Complet, standard du marché Complet, très bonne revue Complet
CI intégrée GitHub Actions GitLab CI — excellente, souvent citée en référence Pipelines, plus limitée
Veille des dépendances Dependabot natif, zéro intégration Intégré, mais surtout en édition payante Via un outil tiers

Ce qui a tranché Pas la qualité brute — GitLab CI est au moins aussi bon. C'est la cohérence de l'ensemble : code, CI, tickets, veille et déploiement sur une seule plateforme, donc zéro intégration à maintenir.
Limite assumée Une dépendance forte à un écosystème unique. Elle est atténuée par le fait que Git reste portable et que la CI tient dans un fichier YAML de 60 lignes, réécrivable ailleurs en une demi-journée.

Ne pas caricaturer GitLab : c'est un très bon produit, et sa CI est une référence — surtout en auto-hébergé. Mon argument n'est pas « GitHub est meilleur », c'est « GitHub me donne l'ensemble cohérent » : Actions, Issues, Dependabot et l'intégration Vercel native, sans coller cinq outils entre eux. Terminer par la limite assumée : ça montre que le choix est réfléchi, pas subi.

06 Déployer

Automatisation · intégration continue

Le pipeline qui garde la production

VI.A.2

.github/workflows/ci.yml — 10 étapes

  1. 01 checkout du code
  2. 02 Node.js 20 avec cache npm
  3. 03 service PostgreSQL 16 conteneur jetable
  4. 04 npm ci installation reproductible
  5. 05 prisma generate
  6. 06 prisma migrate deploy migrations testées
  7. 07 npm run lint ESLint — bloquant
  8. 08 npm run typecheck TypeScript — bloquant
  9. 09 npm run test:run 34 tests Vitest — bloquant
  10. 10 npm run build build de production

Déclencheurs

  • Chaque push sur main
  • Chaque Pull Request vers main

Une base jetable à chaque exécution

Un PostgreSQL 16 neuf est démarré pour le run, les migrations y sont appliquées, puis il disparaît. Les migrations sont donc testées avant la production.

La règle

Une seule étape rouge et la fusion est bloquée. Seul du code qui compile, respecte les conventions et passe les tests peut atteindre la production.

C'est le cœur technique. Montrer que ce n'est pas théorique : ce fichier existe, il tourne à chaque PR. Deux détails à souligner. Un : npm ci installe exactement le lockfile — l'installation est reproductible. Deux : la base PostgreSQL jetable sert à tester les migrations, pas seulement le code — c'est ce qui évite de casser la base de production. Si la démo live est possible, montrer un run vert ici.

07 Déployer

Choix d'outil · automatisation

GitHub Actions, Jenkins, GitLab CI ou CircleCI ?

VI.A.2
Critère GitHub Actions — retenu Jenkins GitLab CI CircleCI
Serveur à maintenir Aucun Oui — à héberger, patcher, sécuriser Aucun (SaaS) Aucun (SaaS)
Configuration YAML dans le dépôt, relu en PR Jenkinsfile + plugins à gérer YAML dans le dépôt YAML dans le dépôt
Lien dépôt ↔ PR Natif — statut affiché sur la PR Via connecteur Natif (sur GitLab) Via connecteur
Coût à ce volume Gratuit Gratuit, mais coût d'infrastructure Gratuit, quota de minutes Quota gratuit limité

L'argument décisif

Jenkins impose un serveur de plus à héberger, mettre à jour et sécuriser. C'est exactement ce que l'architecture serverless cherchait à supprimer : le choix aurait été contradictoire avec le reste.

Ce que l'outil apporte au client

  • Tests intégrés au pipeline : unitaires, composants, migrations
  • Statut visible sur chaque PR : vert ou rouge, sans ambiguïté
  • Suivi des mises à jour : Dependabot ouvre les PR, la CI les valide
  • Historique des exécutions : qui, quand, quoi, pourquoi c'est tombé

La ligne à retenir : « Jenkins, c'est un serveur de plus à sécuriser ». Cohérence du système : j'ai choisi le serverless pour ne pas administrer de machine, je ne vais pas en réintroduire une pour la CI. Le panneau de droite répond directement au cahier des charges, qui demande « le détail des fonctionnalités utiles pour le Ministère ». Si on me demande les tests de performance : ils ne sont pas encore dans le pipeline — Playwright est en place pour l'E2E, les tests de charge sont dans mes pistes d'amélioration.

08 Déployer

Déploiement continu

Livrer sans coupure — et savoir revenir en arrière

VI.A.2

Une PR = un environnement

Chaque Pull Request génère un déploiement Preview isolé, avec sa propre URL.

  • Validation visuelle avant fusion
  • Partageable par lien pour la recette
  • Créé et détruit automatiquement

Fusion = mise en production

La fusion sur main déclenche le déploiement, sans intervention.

  • Install, prisma generate, build Next.js
  • Bascule atomique : pas de coupure
  • Smoke test des parcours critiques ensuite

Retour arrière, deux niveaux

  • Instant Rollback Vercel — le déploiement précédent est re-promu en un clic, sans rebuild
  • git revert côté code, puis nouvelle PR : le correctif repasse par la CI et l'historique reste cohérent

Le point dur : la base de données

Un rollback applicatif ne défait pas une migration. Les migrations sont donc conçues additives autant que possible — on ajoute une colonne plutôt qu'on n'en supprime — pour qu'une version antérieure de l'application reste compatible avec le schéma en place.

CI puis CD La CI valide, le CD livre. Séparer les deux permet de bloquer une livraison sans bloquer le développement.

L'encadré sur la base est le détail qui fait la différence devant un jury : beaucoup présentent le rollback comme un bouton magique. Un rollback applicatif ne défait pas une migration — d'où la règle des migrations additives. Question probable : « comment revenez-vous en arrière en prod ? » → Instant Rollback pour l'urgence (secondes), git revert + PR pour la correction propre.

09 Maintenir

Suivi des anomalies et des évolutions

Le ticketing : GitHub Issues + Projects

VI.A

Gabarit « Anomalie »

  • Description du problème
  • Étapes de reproduction
  • Comportement attendu
  • Criticité — liste imposée
  • Environnement concerné
  • Contexte : navigateur, OS, captures

Gabarit « Évolution »

  • Besoin exprimé
  • Solution proposée
  • Module concerné
  • Priorité
  • Critères d'acceptation

Le tableau de suivi

  • À qualifier
  • À faire
  • En cours
  • En revue
  • Terminé

Étiquettes : bug, enhancement, priority:high, dependencies, maintenance.

Des formulaires, pas des boîtes vides

La saisie libre est désactivée : un ticket sans étapes de reproduction ni criticité ne peut pas être ouvert. La qualification commence à la déclaration.

Une faille ne s'ouvre pas en public

Le formulaire renvoie vers un security advisory privé : signaler une vulnérabilité dans une issue publique reviendrait à la divulguer avant de l'avoir corrigée.

Deux choses à mettre en avant. Un : ce sont des formulaires, pas des issues libres — la saisie blanche est désactivée, donc chaque ticket arrive déjà qualifié. Deux : le renvoi vers l'advisory privé, qui montre que la sécurité est pensée jusque dans l'outil de ticketing. Si le board Projects est visible en démo, l'ouvrir ici.

Le ticket et le code ne se quittent pas

Une issue est liée à sa branche, à sa Pull Request et à ses commits. Écrire Closes #42 dans la PR ferme le ticket à la fusion — donc au moment exact où le correctif part en production.

Aucune double saisie, aucun tableau à remettre à jour à la main.

Le cycle en sept étapes est la réponse à « comment traitez-vous une anomalie ». Appuyer sur l'étape 2, la qualification : on reproduit avant de classer, et la criticité détermine le délai — c'est ce qui rend l'engagement tenable. Et sur l'étape 7 : la clôture est automatique, le ticket se ferme au moment où le correctif atteint la production. Pas de décalage entre l'outil et la réalité.

11 Maintenir

Choix d'outil · ticketing

GitHub Issues plutôt que Jira

VI.A
Critère GitHub Issues — retenu Jira Trello / Linear
Lien avec le code Direct — issue ↔ branche ↔ PR ↔ commit Via connecteur à configurer et maintenir Faible à partiel
Workflows personnalisés Simples : étiquettes + colonnes Très riches — transitions, champs, règles Simples
Reporting agile Basique Avancé — burndown, vélocité, sprints Variable
Coût sur ce projet Gratuit, déjà là Payant par utilisateur Gratuit puis payant
Charge d'administration Nulle Réelle — configuration et synchronisation Faible

Ce qui a tranché

La proximité du code. Un ticket, une branche, une PR, un commit, une mise en production : une seule chaîne, aucune synchronisation entre deux outils — et donc rien qui puisse diverger.

Limite assumée Jira est plus puissant, ce n'est pas discutable : workflows sur mesure, reporting agile, gestion multi-équipes. Sur une équipe de dix personnes avec des sprints formalisés, je choisirais probablement Jira. Ici il serait surdimensionné et payant pour un besoin que les Issues couvrent entièrement.

Ne pas dire « Jira c'est trop lourd » sans nuance : reconnaître d'abord sa supériorité fonctionnelle, puis expliquer que la puissance non utilisée est un coût, pas un avantage. La phrase à garder : « sur une équipe de dix avec des sprints, je choisirais Jira ; ici, ce serait payer et administrer un outil pour des fonctions que je n'utiliserais pas ». C'est ce recul que le jury cherche.

12 Maintenir

Veille technologique

Dependabot — et ce qu'un incident réel m'a appris

VI.A.2

La veille outillée

  • Analyse hebdomadaire des dépendances npm et des actions de CI
  • Mises à jour mineures et correctives regroupées en une seule PR
  • Montées de version majeures ignorées par l'automatisme
  • Alertes de sécurité GitHub sur CVE, en temps réel

Complétée par une veille humaine : CHANGELOG et blogs officiels (Next.js, Prisma, Better Auth), OWASP, annonces de fin de support Node.js.

Retour d'expérience — l'incident

Une vague de PR automatiques majeures — Next 16, Prisma 7, Zod 4, ESLint 10 — a été fusionnée d'un coup. Résultat : build et déploiement cassés. Prisma 7 supprimait les propriétés url et directUrl du schéma, Zod 4 changeait son API.

La cause aggravante : Vercel installe les dépendances avec npm install, pas npm ci — il prend donc la dernière version du range SemVer, et non celle du lockfile validé en CI. La production ne recevait pas ce que la CI avait testé.

Correction : revert vers l'état stable, puis durcissement de Dependabot — les majeures ne sont plus proposées automatiquement, elles sont traitées une par une, sur une branche dédiée.

La leçon

Veille ≠ adoption. Être informé d'une nouvelle version majeure est nécessaire ; la déployer sans l'avoir testée est une prise de risque. La veille reste automatique, l'adoption redevient une décision.

C'est la slide qui montre le plus de recul — ne pas la survoler. Assumer l'incident : je l'ai provoqué en fusionnant des majeures sans les tester, et ça a cassé la production. Le point technique fin, qui impressionne : Vercel installe en npm install, pas npm ci — donc la prod peut recevoir des versions que la CI n'a jamais vues. C'est exactement le genre d'écart qu'on ne découvre qu'en production. Conclure sur « veille ≠ adoption ».

Défense en profondeur

Plusieurs CVE visent un contournement du middleware Next.js. La sécurité ne repose donc pas sur lui : chaque procédure sensible est revérifiée côté serveur dans tRPC.

Chiffrement

  • En transit — TLS partout, sslmode=require
  • Au repos — chiffrement Neon
  • Mots de passe — hachés, jamais réversibles
  • Secrets — variables chiffrées Vercel, jamais dans Git

Chiffres réels, pas théoriques : 41 vulnérabilités relevées, 23 ramenées à 8. Assumer les 8 restantes — elles exigent des montées majeures, donc elles sont planifiées, pas oubliées (cohérent avec la slide précédente). Le point fort ici est la défense en profondeur : j'utilise le middleware, mais je sais qu'il est contournable, donc je revérifie côté serveur. Et sur les secrets : vérifié, aucun .env n'a jamais été commité.

Escalade de l'information

  • Responsable du projet — qualifie l'incident et décide du confinement
  • DPO — saisi dès qu'une donnée personnelle peut être touchée
  • CNIL — notification sous 72 heures en cas de violation
  • Utilisateurs — informés si le risque pour eux est élevé

La descente d'information suit le même chemin : l'incident n'est clos qu'une fois le post-mortem partagé.

Données personnelles collectées

Nom, adresse e-mail, mot de passe haché. Rien de plus — principe de minimisation.

  • Politique de confidentialité et mentions légales publiées
  • Accès, rectification, suppression du compte
  • Suppression des données à la clôture

Deux choix qui servent le RGPD

  • Better Auth auto-hébergé : les données d'authentification restent dans notre base, pas chez un tiers facturé à l'utilisateur
  • Un sous-traitant de moins à encadrer au sens de l'art. 28 : aucune donnée de compte confiée à un service d'authentification tiers

Vigilance : un futur tracker d'émotions manipulerait des données de santé (art. 9) — consentement explicite et garanties renforcées. Hors périmètre livré, mais documenté.

Le cahier des charges demande explicitement les niveaux d'escalade et les conditions de remontée : c'est le panneau de gauche, avec les 72 heures CNIL comme repère chiffré. Sur le RGPD, l'argument que peu de candidats ont : Better Auth est auto-hébergé, donc les données d'authentification ne partent pas chez un tiers — c'est un choix technique qui a une conséquence juridique directe. Terminer sur les données de santé : hors périmètre, mais identifié — ça montre que la question a été posée.

15 Bilan

Conclusion

Une chaîne cohérente, et ce qu'il reste à faire

Un écosystème, pas une collection d'outils

GitHub et Vercel couvrent code, CI, tickets, veille et déploiement. Moins d'intégrations à maintenir — un facteur de pérennité décisif pour un projet porté par une seule personne.

Chaque choix a une raison — et une limite

GitLab CI est excellent, Jira est plus puissant, un VPS coûterait moins cher à charge stable. J'ai choisi selon ce projet : sa charge, son équipe, son budget.

Des faits, pas des intentions

CI remise au vert, vulnérabilités ramenées de 23 à 8, blocage de déploiement corrigé, incident de montée de version géré et documenté.

Pistes d'amélioration

  • Monitoring et alerting — logs et disponibilité
  • CodeQL — analyse statique de sécurité en CI
  • Tests de charge — valider le dimensionnement
  • Adoption testée des majeures : Next 16, Prisma 7

Ce que je retiens

Une chaîne CI/CD ne se juge pas quand tout va bien, mais le jour où elle bloque quelque chose — une PR rouge, un déploiement cassé, une dépendance vulnérable.

Sur ce projet, c'est arrivé. La chaîne a joué son rôle : elle a rendu l'incident visible, réversible et documenté. C'est exactement ce qu'on attend d'elle.

Merci Je suis à votre disposition pour vos questions.

Ne pas réciter le dossier : trois messages, c'est tout. Un — un écosystème cohérent plutôt qu'une collection d'outils. Deux — chaque choix assume sa limite. Trois — des faits vérifiables, pas des intentions. Puis la formule de clôture : une chaîne CI/CD se juge le jour où elle bloque quelque chose. Enchaîner sur les questions.
